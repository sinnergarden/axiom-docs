# 设计与 PRD 维护约定

状态：`draft` · 2026-10-04 · 按已明确的维护方向整理，待审阅。

**正文与新需求。** [主设计与 PRD](design/README.md)记录当前已确认的方案。新需求先写短草案：问题、影响边界、验收条件；讨论确认后更新对应主章节。普通补充直接并入正文。跨模块或改变合同的裁决保留简短原因，链接到生效章节，避免复制另一份完整设计。

**状态与确认。** 草案或裁决在文件或适用段落注明状态；确认记录包含日期、确认人、适用范围及讨论依据，引用固定 commit 与章节。已有文档的确认依据需核实，不能补造。

| 状态 | 含义 |
|---|---|
| `draft` | 待讨论或待确认；不自动替换现行方案。 |
| `accepted` | 该范围已明确确认；设计确认与实现验收分别记录。 |
| `superseded` | 已被新的已确认正文取代；链接替代章节与版本。 |

**版本与入口。** 默认分支是日常入口，定稿引用指向已确认版本。未合并分支须写明基线、状态和固定 commit；已确认但未合入的内容注明“`accepted`，未合入”，并同时链接当前正文与确认版本。推送、代码审查或父任务 review 通过不等于用户已确认产品功能、指标或取舍；合入本身也不能补足缺失的确认。文档冲突先协调裁决，不以最新修改时间决定效力。

**PR 与远端同步。** 用户于 2026-10-04 明确要求通过 PR 留下审查和合并记录：功能分支 → draft PR → 独立 review 与相关检查 → 主协调亲审 → merge PR。不能直接 push 默认分支。PR 写明基准、具体范围、依赖和验证；统一设计的并行分支先核对共享章节，再归入一份生效正文和整合 PR，不覆盖 owner 改动或复制第二张权威表。持续公开授权只包括代码、测试与公共文档，原始数据、凭证和私人研究产物留在本地。

**补丁归位与历史。** 补丁是过渡。吸收后注明“已合入”及主章节；被替代的条款标 `superseded`。部分吸收只标对应条款，不把整份提前作废。[补丁 A](design/07_重要补丁_A.md)与[补丁 B](design/07_重要补丁_B.md)后续逐条核对并归入 01–06；本轮保留原语义与覆盖顺序。财报补充合同对齐 Data 主章节，UI 草案确认后对齐 UI 主章节或其唯一链接 PRD。Git 保存演变，不另存多份“最终版”；必要的历史链接保留。

**目标与实际。** 主设计记录目标；[当前交付](current-delivery.md)与[适用代码版本](../versions.json)记录实现、证据及缺口。区分保存输出、新执行、合成检查和未完成验收。现有代码不能反向自动成为设计裁决，通过小样本也不能记作全量完成。

**单一来源。** 代码、教程和图示引用同一设计版本。教程正文、代码及保存输出由 notebook 维护，图示由明确的源稿与数据维护；HTML、Library、截图和打包附件是生成交付，标明来源版本，修改回到源文件，不形成另一套手写正文。

**周期与触发。** 2026-10-04 明确的持续复审方向：每月轻量复审先看整体，再选择近期变化或风险最高的模块。里程碑、跨模块职责或时间语义变化、正确性反例、重复绕路及维护成本增长触发专项。复审重新检验目标、边界与替代方案，不把既有实现视为不可改变的前提；既有证据足够时不机械全量重测。

| 视角 | 核对重点 |
|---|---|
| 开发者 | 单一职责、重复规则、失败与恢复、变更耦合、存储及执行成本 |
| 研究者 | PIT 可知性、样本成员、特征/标签时序、对照与 OOS、交易成本、结果解释和未检查范围 |

**独立审阅与归位。** 审阅独立于本次实现者，复用已有检查与真实案例，简记问题、证据、影响、建议和未知。已定决策并入对应主章节；普通局部发现不要求新建平台、协议或长篇流程。协作代理组织协调并提出取舍，用户确定研究目标、优先级及实质设计选择。当前 ETF 产物的证据文件占约 98.72%，是后续成本复盘的线索，不触发本轮重构。

**里程碑讲解。** 用约 30 分钟的真实运行，从输入到结果、风险及恢复，帮助用户回答：当时为何可知；与上次改了什么；为何交易或未成交；修订、缺失或异常重跑在哪里定位。讲解保留未知和限制，既不是收益承诺，也不代替对应验收。
